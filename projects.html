Building a Fundamentals-Driven Stock Screener

2026-01-04 permalink

Most stock screeners are glorified spreadsheet filters. You set P/E < 15, dividend yield > 3%, and hope for the best. The problem is that cheap stocks are often cheap for a reason. Value investing isn't just about finding low multiples. It's about finding quality businesses trading below intrinsic value, with competent management and identifiable catalysts for re-rating.

The spark for this project came from reading Double Vision, a piece about exploiting price discrepancies between share classes of the same company. Samsung preferred shares trading at a 24% discount to common, TSMC ADRs at a premium to local shares. The thesis is simple: structural inefficiencies exist because of index inclusion rules, passive investing mechanics, and liquidity preferences. The market isn't always efficient; sometimes you can get more bang for your buck by looking where others aren't.

That idea stuck with me. If structural inefficiencies exist in share class arbitrage, they almost certainly exist in fundamental valuation too. Companies with identical quality metrics trade at wildly different multiples because of sector misclassification, neglect by analysts, or temporary headline risk. The question became: could you systematically surface these opportunities?

This post walks through the architecture of a stock screening system designed around this philosophy: a four-factor framework that combines Value, Business Quality, Capital Allocation, and Catalysts into a single composite score. The stack is Python 3.11, TimescaleDB for time-series storage, and Polygon.io for market data.

The problem with simple screeners

Traditional screeners fail in predictable ways. Value traps: low P/E stocks that stay low forever because the business is deteriorating. Static snapshots: no sense of trajectory. Is ROE improving or declining? Missing context: a 5% dividend yield means nothing if the company is diluting shareholders 10% annually. No confidence scoring: all metrics treated equally regardless of data quality.

The goal was to build something smarter: a system that ingests raw financial data, calculates intrinsic value with confidence intervals, scores companies across multiple dimensions, and surfaces the top 30 opportunities with full audit trails.

Architecture

Why TimescaleDB?

Financial data is inherently time-series. You're constantly asking questions like "What was AAPL's FCF for the last 5 years?" or "Show me all stocks where ROE has improved for 3 consecutive quarters."

TimescaleDB is PostgreSQL with a time-series extension. The key feature is hypertables. Tables that automatically partition by time. Our daily_metrics table stores OHLCV data plus fundamentals (P/E, P/B, ROE, FCF, etc.) for every ticker, every day. Without partitioning, this table would become a performance nightmare. With hypertables partitioned by month, queries stay fast even with millions of rows.

SELECT create_hypertable('daily_metrics', 'date', chunk_time_interval => INTERVAL '1 month');

The composite primary key is (ticker, date), which allows efficient lookups like "give me MSFT's metrics for the last 90 days" without scanning the entire table.

Rate limiting: token bucket algorithm

Polygon.io allows 1000 requests per minute. Naive approaches (sleeping 60ms between requests) waste burst capacity and make ingestion painfully slow.

The solution is a token bucket rate limiter:

class RateLimiter:
    def __init__(self, max_tokens: int = 1000, refill_rate: float = None):
        self.max_tokens = max_tokens
        self.refill_rate = refill_rate or (max_tokens / 60.0)  # 16.67/sec
        self.tokens = float(max_tokens)
        self.last_refill = time.time()
        self._lock = asyncio.Lock()

    async def acquire(self, tokens: int = 1):
        async with self._lock:
            while True:
                now = time.time()
                elapsed = now - self.last_refill
                self.tokens = min(self.max_tokens, self.tokens + elapsed * self.refill_rate)
                self.last_refill = now

                if self.tokens >= tokens:
                    self.tokens -= tokens
                    return

                wait_time = (tokens - self.tokens) / self.refill_rate
                await asyncio.sleep(wait_time)

This allows burst requests up to 1000, then refills at ~16.67 tokens/second. The async lock ensures thread safety without blocking the event loop. When tokens are depleted, it calculates the exact wait time rather than polling.

Intrinsic value with confidence scoring

DCF models are notoriously sensitive to assumptions. A small change in growth rate or discount rate can swing the output by 50%. Rather than pretending precision we don't have, the system calculates a confidence score alongside every valuation.

@dataclass
class IntrinsicValueResult:
    dcf_value: Optional[float]
    dcf_confidence: float  # 0-1
    relative_value: Optional[float]
    relative_confidence: float
    consensus_value: Optional[float]
    margin_of_safety: Optional[float]

Confidence is penalized for: high FCF volatility (if free cash flow swings wildly year-to-year, the projection is less reliable), short history (less than 3 years of data means lower confidence), unrealistic growth rates (projecting 25% growth forever gets discounted), negative FCF in history (one bad year is okay; three is a pattern), and terminal value dominance (if >90% of DCF value comes from terminal value, the model is basically a guess).

The final intrinsic value is a confidence-weighted average of DCF and relative valuation (sector median P/E × EPS). This prevents a shaky DCF estimate from dominating when relative valuation is more reliable.

The four-factor framework

Each stock is scored across four dimensions:

FactorWeightWhat It Measures
Value35%Sector-relative valuation composite (P/E, P/B, EV/EBITDA vs peers)
Quality30%Business fundamentals (ROE, margins, consistency)
Capital Allocation20%Buybacks, dividends, debt paydown, insider buying
Catalysts15%Events that could trigger re-rating (earnings beats, insider clusters)

Weights sum to 1.0 (enforced by dataclass validation). The composite score is a simple weighted sum, but the real value is in the threshold checks.

Avoiding value traps

Beyond the composite score, stocks must pass a series of gates:

@dataclass
class ScoringThresholds:
    min_value_score: float = 50.0
    min_quality_score: float = 60.0
    min_capital_allocation_score: float = 50.0
    min_dollar_volume: float = 1_000_000  # Liquidity
    max_debt_to_equity: float = 3.0
    min_momentum_score: float = 20.0  # Avoid falling knives
    max_share_change_3y: float = 0.25  # Avoid diluters
    max_net_debt_to_ebitda: float = 4.0

A stock can have a high composite score but still fail if it's illiquid, highly leveraged, or has been diluting shareholders. The value_trap_flags field accumulates warnings like "negative_momentum", "dilution", "high_leverage" so you can see exactly why a stock was excluded.

Momentum is treated as a veto and tie-breaker, not a core factor. Cheap stocks with terrible momentum tend to get cheaper. The system excludes the bottom quintile of momentum but doesn't chase high-flyers.

Lessons learned

Confidence > Precision. Financial models are approximations. Surfacing uncertainty explicitly (via confidence scores) is more valuable than pretending you have a precise answer.

Rate limiters are infrastructure. The token bucket pattern appears everywhere: API clients, database connection pools, message queues. Implementing it once with proper async support saves time later.

Time-series databases are worth it. You can hack time-series queries in regular Postgres with clever indexing. But hypertables, automatic partitioning, and time-series-aware query planning make TimescaleDB worth the complexity for financial data.

Veto logic matters as much as scoring. The threshold checks and value-trap flags often provide more insight than the composite score itself. A stock that fails on dilution and negative_momentum is a very different proposition than one that fails on liquidity.

What's next

The current system runs batch ingestion nightly. Future work includes real-time price updates via WebSocket, a backtesting engine to validate the four-factor model against historical returns, a frontend dashboard (React + TanStack Table) for interactive exploration, and an alert system for significant insider buying or catalyst triggers.

The full codebase is modular: swap out Polygon.io for another data source, adjust the factor weights, add new signals. The goal was to build a foundation for systematic value investing that's transparent about its assumptions and honest about its uncertainty.

Building a Stock Analysis Agent with LangChain

2025-12-31 permalink

I wanted to build something that could pull stock data and actually say something useful about it. Not just "here's the price" but "here's what's interesting about this stock right now." The kind of summary a human analyst would write.

The result: a LangChain agent that fetches data from Polygon.io, feeds it to Claude, and returns structured analysis. The interesting parts were getting LangChain's tooling to work smoothly and building evals to catch when the LLM hallucinates numbers.

Polygon.io ──▶ LangChain Tools ──▶ Claude ──▶ Structured Output
     │                                              │
     └──────────── LangSmith Tracing ───────────────┘

The @tool decorator

LangChain's @tool decorator is the cleanest part of the framework. Slap it on a function, write a good docstring, and you've got an LLM-callable tool:

@tool
def get_stock_snapshot(ticker: str) -> dict:
    """Fetch current stock price, volume, and day's high/low."""
    data = requests.get(f"https://api.polygon.io/v2/snapshot/.../tickers/{ticker}",
                        params={"apiKey": API_KEY}).json()
    return {
        "current_price": data["ticker"]["lastTrade"]["p"],
        "volume": data["ticker"]["day"]["v"],
    }

I built three of these: one for real-time snapshots, one for 30-day aggregates, one for company info. The docstrings matter. They're what the LLM sees when deciding which tool to call.

Forcing structured output

The problem with just asking Claude "analyze this stock" is you get prose. Sometimes it mentions risk factors, sometimes it doesn't. Sometimes the format changes. Pain to parse.

Pydantic fixes this:

class StockAnalysis(BaseModel):
    ticker: str
    key_metrics: str
    price_trend: str
    risk_factors: str
    overall_summary: str

Then llm.with_structured_output(StockAnalysis) forces Claude to fill in every field. No more optional sections.

LCEL chains

LangChain Expression Language took me a bit to grok. The | operator pipes data through stages:

chain = (
    RunnablePassthrough()
    | RunnableLambda(gather_stock_data)  # calls all 3 Polygon tools
    | analysis_prompt
    | structured_llm
)

One gotcha: prompt templates can't access nested dicts. So gather_stock_data has to flatten everything. snapshot["day"]["high"] becomes just day_high. Annoying but manageable.

The interesting part: evals

Here's what I actually spent most of my time on. It's easy to get a demo working. It's hard to know if it's good.

LangSmith lets you define test cases and custom evaluators. My evaluators check:

  • Expected mentions: Does the AAPL analysis actually mention "Apple"?
  • Cites numbers: Are there dollar signs and percentages? (Surprisingly often, no)
  • Hallucination detection: This one matters most

The hallucination evaluator compares numbers in the output against numbers in the input. If Claude says "market cap of $2.8T" but the input said $2.5T, that's a flag.

def check_hallucinations(run: Run, example: Example) -> dict:
    output_numbers = extract_numbers(str(run.outputs))
    input_numbers = extract_numbers(str(run.inputs))

    matched = [n for n in output_numbers if any(close_enough(n, i) for i in input_numbers)]
    hallucination_rate = 1 - (len(matched) / len(output_numbers))

    return {"key": "hallucinations", "score": 1 - hallucination_rate}

Running evals:

results = evaluate(
    lambda inputs: chain.invoke(inputs),
    data="stock-analysis-test",
    evaluators=[check_cites_numbers, check_hallucinations, ...],
)

Sample output:

Example 1/4: AAPL
  ✅ expected_mentions: 1.0 (Found 3/3: Apple, market cap, volume)
  ✅ cites_numbers: 1.0 (Found 12 numbers)
  ✅ hallucinations: 0.95 (Matched 11/12 numbers)

Example 2/4: TSLA
  ⚠️ hallucinations: 0.87 (2 numbers not found in input)

Aggregate: 0.91 hallucination score

That TSLA result is the kind of thing you only catch with evals. The analysis looked fine. The numbers were wrong.

Running it

python src/main.py --ticker NVDA

What I'd do differently

Polygon's free tier only allows 5 API calls/minute. Should've added Redis caching from the start. Also, the three tool calls run sequentially. They could be parallel since they're independent.

The hallucination evaluator is crude. It just looks for number matches within 5% tolerance. A better version would understand that "nearly $3T" matching "$2.8T" is probably fine, but "$180 price target" appearing from nowhere is not.
